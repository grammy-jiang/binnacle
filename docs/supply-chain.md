# Binnacle Supply-Chain, Release, Update, and Rollback Security

- **Status:** Draft — mandatory release and deployment contract
- **Related contracts:** `MCP-PROFILE`, `MCP-INTERFACE`, `SELF-MANAGE`, `CAP-LIFECYCLE`, `RELEASE-GATE`
- **Feature-design basis:** [`design.md`](design.md), V17
- **Tool metadata integrity:** [`mcp-tool-manifest.md`](mcp-tool-manifest.md)
- **Audit integrity:** [`audit-evidence.md`](audit-evidence.md)
- **Last review:** 2026-08-08

## 1. Purpose

This document defines how Binnacle selects, pins, builds, inventories, scans, signs, verifies, installs, starts, updates, rolls back, and retires its software supply chain.

Binnacle executes commands and controls a Raspberry Pi. A compromised MCP SDK, tunnel agent, build dependency, package, installer, runtime, or update channel can therefore bypass every higher-level Tool and policy contract. Supply-chain evidence is a release prerequisite, not optional documentation.

The governing rules are:

> Every installed executable and security-relevant runtime component is traceable to an approved source and an immutable release record.

> A version label, Git tag, package name, latest channel, container tag, or download URL without an authenticated digest is not an immutable pin.

> A signature generated by the same untrusted runtime does not establish release trust. Signing and verification roots are separated from the installed Binnacle process.

> Reproducibility is claimed only at the level demonstrated by independent rebuild evidence; the project must not promise bit-for-bit reproducibility before the selected toolchain proves it.

## 2. Assurance States

A build has one supply-chain state:

| State | Meaning | Permitted use |
| --- | --- | --- |
| `development-unverified` | Local source or dependencies are not fully pinned or release evidence is incomplete | Local development only; no supported remote operation |
| `preview-verified` | Source, dependencies, build inputs, artifact digests, SBOM, provenance, and installation checks are complete for an engineering preview | Frozen private preview profile only |
| `release-candidate` | Preview evidence plus required security, compatibility, migration, update, and rollback gates pass | Staged canary deployment only |
| `supported-release` | Release candidate is independently signed/attested, published through the approved channel, and passes release acceptance | Supported Personal V1 profiles |
| `restricted` | Installed build is unknown, modified, vulnerable beyond policy, unverifiable, revoked, or outside its support window | Bounded status, evidence, safe stop, local recovery, and upgrade only |
| `retired` | Build is explicitly outside support and may be blocked by local retirement policy | No normal operation; migration or local recovery only |

A later state cannot be inferred from successful execution alone.

## 3. Approved Sources and Immutable Pinning

### 3.1 Source repository

A release binds to:

- canonical repository identity;
- exact commit SHA;
- source tree digest or archive digest;
- expected branch/tag only as descriptive metadata;
- signed tag or commit verification where the selected governance profile requires it;
- submodule and generated-source identities;
- release-policy and build-definition versions.

A mutable branch, unverified fork, pull-request head, or tag without the expected commit and trust evidence cannot be used for a supported release.

### 3.2 Language and build dependencies

Every direct and transitive build or runtime dependency must be represented in an approved component lock with:

- canonical package/ecosystem identity;
- exact version;
- source registry or repository;
- artifact filename and platform selector;
- cryptographic digest for every accepted artifact;
- package URL or equivalent identity;
- license expression and policy result;
- source and binary relationship where available;
- dependency type: build, runtime, test, optional, or development;
- reason and owning Binnacle component;
- vulnerability and exception state;
- update and end-of-support facts.

Resolution from floating ranges during a release build is prohibited. Lockfiles without artifact hashes are insufficient for a supported release unless the ecosystem cannot supply immutable artifacts and a separately reviewed equivalent is documented.

### 3.3 MCP SDK

The MCP SDK is security-critical. The selected release record must pin:

- SDK package and exact version;
- every accepted artifact digest;
- source commit/release provenance where available;
- transitive dependency lock;
- supported MCP revisions and adapter profile;
- local patches and their digests;
- conformance-test result;
- vulnerability and maintenance status.

An SDK update reopens revision, wire-schema, authentication, Tool metadata, cancellation, and compatibility regressions. SDK capability does not silently expand Binnacle's supported MCP features.

### 3.4 Tunnel and gateway components

A local tunnel, reverse connector, proxy, or gateway binary must be pinned by exact version and artifact digest and must have a recorded publisher/signature result.

A remotely operated tunnel service may not expose a customer-verifiable service artifact digest. In that case, the profile records separately:

- service/provider identity;
- local agent artifact and digest;
- account/workspace and security configuration digest;
- service release/build identity when exposed;
- vendor provenance or attestation when available;
- observed behavior and compatibility evidence;
- contractual and operational dependency limits;
- incident, revocation, and replacement path.

The absence of a service artifact digest must not be hidden by inventing one. It is an external-dependency residual risk and can block a supported profile if the security policy requires stronger evidence.

### 3.5 Base operating system and native components

The deployed inventory records:

- Raspberry Pi model and architecture;
- OS distribution and release;
- kernel identity;
- boot firmware where relevant;
- system libraries loaded by Binnacle or its broker;
- service manager and sandbox/security components;
- local tunnel/gateway agent;
- package source and installed package versions;
- configuration and security-profile digests.

Host-wide OS reproducibility is not implied by a reproducible Binnacle package. The selected device profile states which OS components are release prerequisites and which are observed environmental dependencies.

## 4. Component Lock and Release Manifest

### 4.1 Component lock

The project maintains a machine-valid component lock before implementation or release dependencies are accepted.

The lock is generated from reviewed source and resolved dependency inputs, then committed or retained under change control. It is not generated from an already-compromised installed environment and accepted without comparison.

Every change produces an explicit diff and targeted regression.

### 4.2 Release manifest

Each build produces one immutable release manifest conforming to:

```text
schemas/supply-chain/release-manifest.schema.json
```

It binds:

- product, release, source, and build identities;
- supported architecture and OS profile;
- component lock digest;
- output artifact digests and sizes;
- Tool manifest and schema-registry digests;
- policy, device-profile, audit-schema, and migration versions;
- SBOM and provenance identities/digests;
- vulnerability, license, test, MCP compatibility, and host-confirmation results;
- signing identities and transparency/external receipts where used;
- installation and startup verification requirements;
- rollback compatibility and previous safe release;
- release status, support window, and retirement state.

The manifest itself is signed or attested by the approved release authority. Its digest is included in discovery, compatibility evidence, audit, operation evidence, and deployed inventory.

## 5. SBOM

### 5.1 Required SBOMs

A release produces at least:

1. **Source/build SBOM** — build tools, generators, actions, plugins, compilers/interpreters, and build-only materials.
2. **Runtime SBOM** — Binnacle package, runtime libraries, bundled binaries, native extensions, and local agents distributed with the release.
3. **Deployment inventory** — actual installed Binnacle, SDK, tunnel/gateway, runtime, OS/security components, and configuration digests on one Raspberry Pi.

The SBOM format is SPDX- or CycloneDX-compatible, selected by architecture. The policy does not depend on one vendor format.

### 5.2 SBOM content

The SBOM includes, where applicable:

- component name, version, package URL, supplier, and source;
- cryptographic hashes;
- dependency relationships;
- licenses and notices;
- source/binary relationship;
- architecture and platform;
- modification/patch status;
- generated-file provenance;
- known end-of-life status;
- document namespace, creation identity, version, and digest.

Unknown components are explicit and block a supported release unless a narrowly approved exception exists.

### 5.3 Retention

SBOMs, lockfiles, provenance, release manifests, signatures, vulnerability reports, and build logs are retained for the supported life of the release plus the longest security/audit requirement.

## 6. Build Provenance

### 6.1 Required provenance

The build provenance records:

- source repository and commit;
- source tree/archive digest;
- component lock digest;
- builder identity and trust boundary;
- build-definition/workflow identity and digest;
- build invocation and declared parameters;
- build environment image or host identity/digest;
- network policy during build;
- all declared materials and their digests;
- generated outputs and digests;
- start/end time;
- whether the build was isolated, hermetic, and reproducible;
- test and scan evidence digests;
- signer/attester identity;
- external transparency or receipt where selected.

The provenance uses a signed, verifiable statement format chosen by the supply-chain architecture. It must be independently verifiable from the release artifact.

### 6.2 Builder isolation

A supported release builder must:

- start from an approved clean environment;
- use locked materials;
- prevent unrecorded dependency resolution;
- restrict or deny network access after materials are fetched;
- isolate secrets from build scripts and output;
- avoid unsigned arbitrary pull-request code in a privileged signing context;
- generate outputs in a new location;
- record all build steps and materials;
- separate build identity from release-signing authority.

### 6.3 Reproducibility levels

Binnacle records one demonstrated level:

| Level | Claim |
| --- | --- |
| `RB0-unassessed` | No reproducibility claim |
| `RB1-resolved-inputs` | Same approved source and component lock are used; output equality is not claimed |
| `RB2-deterministic-package` | Repeated builds in the same reviewed builder produce the same release payload digest |
| `RB3-independent-rebuild` | At least two independent builders reproduce the same canonical artifact digest |

Preview may begin at RB1 with explicit limitations. A supported release target should reach RB2. RB3 is claimed only after independent evidence; it is not mandatory before the toolchain demonstrates feasibility unless the final security policy makes it a gate.

Timestamp, archive-order, path, locale, generated-ID, dependency metadata, compression, and signing nondeterminism must be normalized or excluded from the reproducible payload. Signatures may be separate from the reproducible unsigned artifact.

## 7. Signing and Trust Roots

### 7.1 Release signing

Supported artifacts and release manifests require an approved signature or equivalent provenance attestation.

The signing authority must be separated from:

- the installed Binnacle runtime;
- ordinary development credentials;
- untrusted pull-request execution;
- mutable release storage;
- the artifact being verified.

The signer identity, key ID, algorithm, validity, revocation, rotation, and recovery policy are versioned.

### 7.2 Keyless or key-backed signing

Architecture may select:

- key-backed signing with protected release keys;
- identity-backed/keyless signing with verifiable issuer, subject, workflow, and transparency evidence;
- another independently verifiable mechanism.

The release policy defines the exact accepted roots and claims. A generic valid signature from an unapproved identity is insufficient.

### 7.3 Root and key changes

Trust-root changes require owner governance and an authenticated local installation/recovery path. A normal remote Tool or general command cannot replace release trust roots.

An expired or revoked signer does not automatically invalidate artifacts validly signed before revocation; the retirement policy determines the result based on revocation reason, signing time evidence, and release status.

## 8. Vulnerability and License Gates

### 8.1 Scan scope

Release scanning includes:

- source and repository secrets;
- direct and transitive language dependencies;
- native libraries and bundled binaries;
- container/base images if used;
- local tunnel/gateway agents;
- relevant OS/runtime packages in the device profile;
- SBOM-based vulnerability matching;
- malware or integrity checks for downloaded artifacts;
- license and notice policy;
- end-of-life and abandoned-component status.

### 8.2 Data freshness

The release record identifies scanner versions, vulnerability databases, timestamps, policies, and results. A scan with a stale or unavailable database cannot be represented as current.

Initial maximum vulnerability-data age for release promotion is 24 hours unless the security policy records a different evidence-backed limit.

### 8.3 Gate policy

A release is blocked by:

- a known actively exploited vulnerability affecting the deployed configuration;
- an unmitigated critical vulnerability;
- a high vulnerability with plausible exploitability across a Binnacle trust boundary, unless a time-bounded exception is approved;
- an unknown or unpinned security-critical component;
- unapproved source or artifact origin;
- a prohibited license or missing required notice;
- a failed secret, malware, signature, provenance, or integrity check;
- an end-of-life component whose risk exceeds policy.

Severity alone is not the complete decision. Reachability, exploitability, compensating controls, protected function, and exposure are recorded.

### 8.4 Exceptions

An exception requires:

- component and vulnerability identity;
- affected builds/profiles;
- exposure and exploitability analysis;
- compensating controls;
- owner/security decision;
- expiry no later than the policy maximum;
- remediation owner and target date;
- monitoring and forced-retirement trigger.

An expired exception blocks new installation and update promotion. Existing deployment follows the retirement policy.

## 9. CI and Release Gates

A release pipeline must fail on:

- uncommitted or untracked release input;
- dependency lock drift;
- missing artifact hashes;
- source or registry outside the allowlist;
- SBOM/provenance/manifest generation failure;
- schema, metadata, interface, policy, audit, and lifecycle validation failure;
- vulnerability, license, secret, malware, or EOL policy failure;
- unit, integration, fault-injection, or compatibility regression;
- target architecture/profile failure;
- unsigned or unapproved artifact;
- inability to install, verify, start, health-check, update, or roll back;
- mismatch among release, Tool manifest, schema, policy, and binary digests.

A skipped required gate is a failure unless the frozen profile prospectively marks it not applicable with rationale.

## 10. Installation Verification

Before installation or update, the installer verifies:

1. release manifest schema and signature/attestation;
2. approved signer/issuer, subject, workflow, and trust root;
3. artifact digest and size;
4. source and component lock relationship;
5. SBOM and provenance digests;
6. target device architecture, OS, and profile compatibility;
7. release status, support window, and retirement policy;
8. required migrations and rollback compatibility;
9. local policy permitting the installation;
10. available storage, recovery, and previous-release retention.

Verification failure produces no installation effect.

The downloaded artifact is stored in a content-addressed staging area and is not executed from a mutable download location.

## 11. Startup and Runtime Verification

Before exposing the remote Tool catalogue, Binnacle verifies:

- installed release-manifest identity and signature/attestation;
- Binnacle executable/package digest;
- Tool manifest, schema registry, policy schema, audit schema, and operation-contract digests;
- critical broker/helper and local-agent identities;
- configuration and device-profile compatibility;
- release not locally revoked, forcibly retired, or outside allowed support state;
- required migration state;
- installed inventory against the release manifest.

A full file-by-file dependency scan need not run on every startup if installation creates a protected immutable environment and an integrity root. The selected architecture must show how startup verification covers the installed runtime and how periodic or on-demand deep verification detects drift.

A mismatch enters `restricted` state. Binnacle must not dynamically bless the observed files as a new release.

## 12. Deployed Inventory and Evidence

Every Binnacle instance retains a deployed-component inventory containing:

- device identity and profile;
- release ID, version, manifest digest, artifact digest, and signer/attester result;
- source commit and component-lock digest;
- MCP SDK, tunnel/gateway, runtime, broker, sandbox, and security-component identities;
- SBOM and provenance references/digests;
- Tool manifest and visible-catalogue digest;
- schema, policy, audit, and migration versions;
- current vulnerability/exception and support state;
- install, update, rollback, and verification times/results.

Sanitized inventory evidence is returned through `binnacle_probe`, `compatibility_report`, operation evidence, and audit. It never exposes private keys, credentials, internal tokens, or unsafe local paths.

## 13. Staged Update

### 13.1 Update is a dedicated operation

Binnacle update is not performed by `command_run`. It uses a dedicated `SELF-MANAGE` operation, HC1 confirmation, local policy, prepared exact release manifest, idempotency, audit, and rollback contract.

### 13.2 Stages

The update lifecycle is:

```text
available → downloaded → verified → staged → preflight_passed
→ activated → health_verifying → accepted
                         ↘ rollback_pending → rolled_back | recovery_required
```

Before activation, Binnacle verifies:

- new release and component evidence;
- current/target version path;
- disk and resource capacity;
- configuration and data migration plan;
- protocol and Tool compatibility;
- security-policy and sandbox compatibility;
- recovery and rollback artifact;
- no unresolved operation that the update would orphan;
- audit and idempotency durability.

### 13.3 Canary and rollout

For multiple owner devices, the first target is a named canary Raspberry Pi. Binnacle instances do not coordinate the rollout; ChatGPT and owner governance do.

Canary acceptance includes:

- installation and startup integrity;
- MCP revision and host-profile probes;
- Tool manifest and schema validation;
- controller authentication;
- read-only and controlled write probes;
- command sandbox tests where enabled;
- operation/idempotency/audit recovery;
- self-management restart and reconnect;
- resource and latency budgets.

Other devices update only after owner acceptance of canary evidence.

### 13.4 Migration

Every persistent-data migration declares:

- source and target versions;
- preconditions;
- backup/snapshot;
- forward transform and verification;
- rollback/reverse transform or explicit non-reversible boundary;
- maximum downtime and storage;
- crash/restart behavior;
- evidence and recovery.

A non-reversible migration requires explicit owner confirmation and a tested forward-recovery path. It cannot claim automatic rollback.

## 14. Rollback

### 14.1 Rollback artifact

Before activation, Binnacle retains the last known safe release artifact, manifest, signature, configuration, migration state, and verification evidence in a protected local location.

Rollback uses only a previously approved artifact. It never downloads `latest` during an incident and never rolls back to an artifact that is retired, revoked, incompatible with current data, or unverifiable.

### 14.2 Automatic rollback

Automatic rollback may occur only under a frozen rule after:

- target startup failure;
- target integrity failure;
- bounded health-check failure;
- inability to re-establish the expected MCP endpoint;
- target migration failure before the non-reversible boundary.

The rule cannot select another arbitrary version. It targets the one recorded rollback artifact.

### 14.3 Rollback result

Rollback success requires verification of:

- old release manifest and artifact;
- service health;
- data/configuration compatibility;
- controller authentication and MCP probe;
- audit and operation-store integrity;
- absence of partially activated target components;
- current vulnerability and retirement policy.

If rollback cannot be verified, the device remains restricted and requires local recovery.

## 15. Vulnerable Build Response and Forced Retirement

### 15.1 Advisory intake

The project continuously or periodically reevaluates retained SBOMs against current vulnerability and retirement data. A new finding creates a signed/approved policy decision identifying affected release manifests and profiles.

### 15.2 Dispositions

| Disposition | Behavior |
| --- | --- |
| `monitor` | Normal support continues with recorded rationale and review date |
| `mitigate` | Compensating policy restricts affected capabilities while update is prepared |
| `block_new_install` | Existing deployment may continue only under stated risk; no new installation or rollback to the build |
| `restricted` | Normal consequential operations disabled; status, evidence, safe stop, update, and local recovery remain |
| `retired` | Normal remote operation disabled; migration/update or local recovery only |
| `emergency_isolate` | Owner follows local/physical isolation; Binnacle cannot claim remote enforcement after highest-boundary compromise |

### 15.3 Retirement authenticity

A remote retirement decision must be authenticated under the owner-governed policy/update trust root and must identify exact release-manifest digests. An unauthenticated network response, issue text, model statement, or package advisory cannot remotely disable Binnacle.

Offline devices apply their last accepted policy and support expiry. The design records the maximum revocation/retirement latency and does not claim immediate remote retirement during disconnection.

### 15.4 Minimum retained function

Restricted or retired builds expose only locally policy-permitted:

- identity and release evidence;
- audit/integrity evidence;
- bounded status;
- cancellation and safe stop;
- verified update/rollback where safe;
- local recovery instructions.

They do not silently re-enable normal operation because the update service is unavailable.

## 16. Recovery and Rebuild

A materially compromised or unverifiable installation is rebuilt from:

- trusted device/OS recovery media or a separately verified base;
- approved Binnacle release manifest and artifact;
- verified policy and device profile;
- retained audit/checkpoint evidence;
- separately restored credentials;
- fresh device/controller trust decision where required.

Restoring files does not restore trust automatically. The rebuilt device must pass installation, startup, MCP, security, and profile verification.

## 17. Validation Files

The canonical policy and tests are:

```text
schemas/supply-chain/release-manifest.schema.json
spec/supply-chain/release-policy.yaml
tests/fixtures/supply-chain/release-security.yaml
```

Required tests cover:

- approved and unapproved sources;
- floating versions and missing hashes;
- dependency substitution and lock drift;
- malicious or mismatched SDK/tunnel artifacts;
- incomplete SBOM and provenance;
- signer, issuer, audience, workflow, and transparency mismatch;
- vulnerability database freshness and policy exceptions;
- license and secret failures;
- clean/repeated/independent build claims;
- install/startup verification and drift;
- staged update, crash at every stage, migration, canary, and health checks;
- rollback success, rollback incompatibility, and rollback to retired/vulnerable build;
- retirement authenticity, offline latency, and minimum function;
- audit/evidence binding.

## 18. Source of Truth

The precedence is:

1. release-manifest schema;
2. release-policy specification;
3. signed/attested release manifest and component lock for one release;
4. this document;
5. package metadata, tags, or examples.

A package manager's success or a server's ability to start does not establish supply-chain validity.
